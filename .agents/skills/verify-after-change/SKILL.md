# 项目变更验证

每次修改代码后都使用此 Skill。不要先在沙箱内试跑验证命令；直接申请沙箱外权限执行受本次变更影响的编译和测试。

## 必须执行

先判断本次修改影响的项目部分，再只运行对应验证。不要因为后端变更去构建 admin，也不要因为 admin 变更去跑后端测试，除非变更会同时影响两边。

## 验证命令

按顺序运行对应范围内的两组验证。第一组是编译/检查，第二组是测试。

### 1. 编译

如果影响后端，运行后端 Go 编译：

```bash
go test -run '^$' ./...
```

如果影响 admin，运行后台管理前端检查与构建：

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm check
pnpm build
```

前端命令必须在 `admin` 目录下运行。

### 2. 测试

如果影响后端，运行后端测试：

```bash
go test -p 1 ./...
```

测试命令必须在项目根目录运行。

运行测试前，检查 `.env` 或当前终端环境中是否有完整的 `TEST_DB_HOST`、`TEST_DB_PORT`、`TEST_DB_USER`、`TEST_DB_PASSWORD`、`TEST_DB_NAME`。如果没有，直接使用 `docker-compose.test.yml` 启动 PostgreSQL 测试容器并等待其可用，再按该文件中的连接信息设置测试环境变量并运行测试。

仅当测试容器由本次验证启动时，测试结束后停止该容器。如果 Docker 不可用、容器启动失败或因其他原因无法完成实际数据库测试，仍需运行 `go test -p 1 ./...`，并在最终回复中明确说明数据库测试未实际完成及具体原因；不得把数据库测试被跳过视为验证完成。

如果只影响 admin 且项目没有 admin 专用测试命令，不需要额外运行后端测试；完成 `pnpm lint`、`pnpm check`、`pnpm build` 即可。

## 执行要求

- 如果某一步失败，保留失败输出的关键错误，修复后重新从相关失败步骤开始验证。
- 最终回复必须说明本次判断的影响范围、实际运行的编译/构建和测试命令，以及失败时的具体阻塞点。
